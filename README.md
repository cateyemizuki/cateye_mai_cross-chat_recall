# 跨聊私聊回忆

MaiBot 扩展插件 `github.cateye.mai-cross-chat-recall`：让 bot 在群聊里“记得”它与群友的私聊内容。

插件按可配置的时机扫描群内活跃用户，读取这些用户与 bot 的私聊，把满足条件的记录交给 LLM 概括并存入插件自建的 SQLite；在群聊的 planner 与 reply 请求中，把相关概括作为一条「【私聊记忆】」系统消息注入模型上下文。bot 也可以通过 LLM 工具 `recall_private_chat` 按昵称主动召回某位群友的私聊概括。

它面向希望 bot 在群里自然延续私聊话题（约定、偏好、近况）的 MaiBot 部署者。私聊内容只作为记忆来源，原文不会被当作消息发到群里。

**边界**：群聊消息用于确定“该看哪些人”；私聊消息只读，仅用于生成概括；总结库不保存私聊原文，只保存概括与必要元数据。常规情况下，扫描的触发与注入只发生在群聊会话；`/ccr debug test` 是例外：它会对当前聊流（包括私聊流）设置强制注入，并让后续 planner / reply 请求跳过群聊检查。标记存在期间，`planner` 模式会在每次 planner 请求时、`reply` 模式会在能反查到被回复用户时继续扫描当前聊流，不论是否已有总结。

## 工作流程

1. **扫描**：按 `scan.trigger_mode` 选时机，取群内最近若干条非 bot 消息的作者作为候选，逐个检查其与 bot 的私聊。
2. **总结**：窗口内用户消息数达标（或已排入重总结队列）时，把窗口内私聊交给 LLM 生成概括，按用户覆盖写入总结库。
3. **注入**：群聊 planner / reply 请求前，把有效概括合并成一个块插入上下文。
4. **召回**：模型可调用 `recall_private_chat` 取回单个用户的概括；召回成功后短时间内继续随 reply 注入。

## 安装与运行条件

- 宿主 MaiBot `1.2.0`–`1.99.99`，MaiBot SDK `2.5.0`–`2.99.99`；插件类型为 `extension`。
- 无第三方依赖，代码只使用标准库与 `maibot_sdk`。
- 将整个插件目录放入 MaiBot 插件目录，在宿主中启用即可；首次加载会自动创建总结库与表，不需要手动初始化。
- 插件在清单中声明以下能力：`send.text`、`chat.get_all_streams`、`chat.get_stream_by_user_id`、`message.get_recent`、`message.get_by_time_in_chat`、`message.get_by_id`、`llm.generate`、`config.get`。
- 运行期文件：
  - 总结库：宿主插件数据目录下的 `cross_chat_recall.db`（典型路径 `data/plugins/<plugin_id>/cross_chat_recall.db`），单表 `private_summaries`，每个用户一行。
  - 日志：插件目录 `logs/cross_chat_recall.log`，见「日志」。
  - 配置：宿主维护并在插件目录生成 `config.toml`；该文件、`logs/`、`data/` 都不应提交到仓库。

## 扫描：什么时候扫、扫谁

`scan.trigger_mode` 三选一：

| 取值 | 触发时机 | 扫描范围 | 频率与开销 |
|---|---|---|---|
| `planner`（默认） | 每次 planner 请求前 | 该群最近 `scan.scan_count` 条非 bot 消息的作者 | 每个 planner 请求一轮；扫描在后台执行，不阻塞 planner |
| `push` | 群内非 bot、非命令、非合成消息累计达到 `scan.scan_count` 条 | 同上 | 每 N 条消息一轮；计数只在内存中，重启清零；群不在作用范围内不计数 |
| `reply` | 每次 reply 且能反查到被回复的用户 | 只扫被回复的那一个用户 | 每次可反查目标的回复一轮，开销最小 |

共同行为：

- 候选用户来自群内最近 `scan.scan_count` 条非 bot 消息（默认 10，范围 1–100），按新→旧去重。bot 自身、通知与插件注入的合成记录不计入；非 bot 消息不足该数时退回全部可用消息。
- 候选逐个过用户黑白名单，然后查该用户与 bot 的私聊流，再拉取窗口内消息。没有私聊流的用户直接跳过。
- 每个用户每轮最多抓取窗口内 500 条私聊消息；达到上限会在日志中警告，总结可能基于被截断的记录。
- 同一进程同时只跑一轮扫描。扫描进行中收到的新触发会把该聊流记入待补扫集合，但不会排队执行：当前扫描结束时只处理发起它的那个聊流自身的补扫登记，其他聊流的登记不会被当前扫描处理；同一聊流的补扫也沿用当前扫描的候选范围，不保留新触发指定的对象。并发触发时可能漏扫。
- 聊天流信息（是否群聊、群号、平台）缓存 60 秒，因此群/私聊判定和群号可能滞后；刷新失败时沿用旧缓存。
- `planner` 模式下扫描由 planner 请求触发，与 `inject.inject_planner` 是否开启无关；关闭注入只停止往上下文里放内容，不停止扫描。

扫描本身的开销是逐个候选查私聊流、拉窗口消息；只有达到总结或重总结条件时才会调用 LLM。`planner` 模式最频繁，`push` 模式随消息量，`reply` 模式每次只处理一个用户。

## 总结：条件、重总结队列与淘汰

- **窗口**：`summarize.window_hours`（默认 24 小时，最小 0.1）。窗口外的私聊消息既不参与判定，也不进入 LLM 请求体。
- **阈值**：窗口内来自对方的私聊消息数（不含 bot 自己）达到 `summarize.min_user_messages`（默认 5，最小 1）。
- **首次**：库里没有该用户的记录且阈值达标 → 立即总结。
- **重总结**：已有记录时，统计时间戳晚于上次总结截止时间的用户消息；达到 `summarize.resummarize_push_count`（默认 5，最小 1）只写入“待重总结”标记，不立即调用 LLM。之后某次扫描命中标记时才全量重写，覆盖旧概括并更新起止时间；命中标记后的重写不再要求本轮消息数重新达标。
- **失败冷却**：总结返回空或调用失败，该用户 600 秒内不再发起总结，避免持续失败时反复消耗 token。
- **请求体**：一条 system 消息（`summarize.prompt`，留空用内置默认；支持 `{bot_name}` / `{user_nickname}` / `{user_id}`）+ 一条 user 消息（该私聊流窗口内的消息，按时间升序，每行 `[YYYY-MM-DD HH:MM:SS] 说话者：内容`；非文本消息标为“（非文本消息）”；末尾附加“只输出概括”的要求）。请求体不含群聊内容。
- **默认提示词**：要求按时间线概括关键事件与时间点、覆盖最近一两次聊天，并以「需记住：」单独一行列出关键事实，总长控制在 400 字以内。
- **模型参数**：`summarize.model` 非空时传给宿主（默认 `replyer`，可填任务名或具体模型名）；指定模型调用失败会去掉 model 重试一次。`summarize.max_tokens` 大于 0 时传入（默认 1024），0 表示不传。
- **入库**：user_id、platform、私聊流 id、昵称、概括正文、起止时间（窗口内消息时间的最小/最大值）、用户消息数、待重总结标记、更新时间。每用户一行，重总结覆盖。
- **TTL**：`store.summary_ttl_hours`（默认 24 小时，最小 0.1）。截止时间早于“现在 − TTL”的概括在注入与工具召回时跳过；扫描处理完候选用户后会从库中删除过期行。

## 注入：planner 与 reply 怎么拿到概括

注入块形如：

```
【私聊记忆】以下是最近一段时间你在私聊中与部分群友的聊天内容概括（仅供你自己参考，帮你记起与对方私下聊过的内容；请自然地运用，不要生硬复述）：
1. 与 星尘（10001）在 2026-09-29 21:31:16 至 2026-09-29 22:05:40的私聊内容概括：
……
```

- 插在 `items` 第一条之后（首条通常是 `SystemMessageItem`）；`items` 为空时只放新块，首条不是 `SystemMessageItem` 时仍插在位置 1。多个用户合并为一个块，按最近私聊时间新→旧排列。
- 只注入未过 TTL 且正文非空的概括；没有有效概括时不改动上下文。

### planner

- `inject.inject_planner`（默认 `true`）控制是否注入。
- `inject.planner_user_mode`：`trigger`（默认）= 触发 planner 的最近一条非 bot 消息作者；`recent_users` = 最近 `inject.recent_user_count` 条非 bot 消息中出现过的用户（默认 5，范围 1–50）。
- 选出的用户过用户黑白名单，无有效概括则不注入。planner 选中的用户会缓存 300 秒，供 reply 的 `follow_planner` 使用。

### reply

- `inject.inject_reply`（默认 `true`）控制是否注入。
- `inject.reply_user_mode`：`reply_source`（默认）= 被回复消息的作者（用 `reply_message_id` 反查）；`follow_planner` = 复用 300 秒内的 planner 用户缓存，缓存不存在或过期则本次不注入。
- `reply_source` 选出的用户过用户黑白名单；工具召回的粘性用户与常规用户合并去重后一起注入，粘性用户不再复查名单。

### 工具召回的粘性块

- 群被群名单排除时，常规 reply 注入跳过；如果该群有未过期的粘性召回用户且 `inject.inject_reply` 开启，则只注入粘性块。
- 非群聊会话不注入粘性块。

### 调试强制注入

- `/ccr debug test` 给当前聊流的 planner 与 reply 分别设置强制注入标记，600 秒（10 分钟）内有效；标记优先于常规路径，绕过群聊、作用范围与注入开关检查，但插件总开关关闭时不执行。
- 标记在注入成功后才消费；当前没有有效概括时保留标记，继续走常规路径。库里没有该用户的非空总结时，命令会先触发一次定向扫描。
- 标记只作用于当前聊流，不要求是群聊，私聊流里也可用于调试。

## LLM 工具：`recall_private_chat`

bot 在群聊里按昵称召回某位群友的私聊概括。

- **参数**：`user_name`（string，必填）——要召回的用户昵称；匹配到多个用户时可改传 QQ 号。
- **可用范围**：仅群聊；非群聊或会话类型未知返回 `success=false` 与“私聊回忆工具仅在群聊中可用。”；插件关闭时返回“私聊回忆功能未启用。”。
- **候选范围**：只取当前聊流最近 `tool.context_window_messages` 条消息（默认 50，范围 5–200）里出现过的用户；bot 自身、通知、合成与命令消息不参与，昵称为空的用户不参与，同一用户取最新昵称。不做全库或全群搜索。
- **名称解析**：
  1. 先按昵称或 QQ 号字符串等值匹配；
  2. 精准未命中时用 `re.search` 匹配昵称（传入非法正则时按字面量）；
  3. 唯一命中 → 查该用户的概括；
  4. 命中多个 → 返回「昵称（QQ 号）」名单（按最近发言新→旧），提示改传昵称或 QQ 号，不附带私聊内容；
  5. 0 命中或名称为空 → 返回“名称有误：当前会话中没有找到名称为「…」的用户。”。
- **返回**：
  - 有有效概括：`success=true`，正文为「【私聊记忆】你与 昵称（QQ 号）在 起始时间 至 截止时间 的私聊内容概括：」加概括；
  - 无记录、概括为空或已过 TTL：`success=true`，内容为“你和该用户没有私聊内容。”；
  - 名称有误或多命中：`success=false`，内容为对应提示。
- **粘性保留**：召回成功后在内存中登记该聊流与用户，`tool.recall_retention_minutes`（默认 5 分钟，范围 0.5–1440）内每次 reply 请求继续注入该用户的概括；再次成功召回会刷新计时。粘性状态不落盘，进程重启即清空；只影响 reply，受插件总开关与 `inject.inject_reply` 门控，仅群聊注册与注入。
- 工具说明要求模型只在用户明确要求回忆私聊内容时调用；是否调用由模型判断，插件不做运行时校验。
- 示例：群里有人问“你还记得私聊里星尘说过什么吗？”，模型可调用 `recall_private_chat(user_name="星尘")`；名称需取自当前会话上下文。

## 斜杠命令

| 命令 | 权限 | 作用 |
|---|---|---|
| `/ccr debug test` | operator | 为当前聊流的下一次 planner 与 reply 设置强制注入，注入命令发起者与 bot 的私聊概括 |
| `/ccr clean` | operator | 清空总结库，并清除所有强制注入与粘性召回标记 |

- 命令前可有空白，`/ccr debug test` 与 `ccr debug test` 都能匹配，`/ccr clean` 同理；两条命令都不接受参数。
- 权限为 `operator`，仅操作员账号可用。
- `debug test`：绕过群聊、作用范围与注入开关；需要能识别当前聊流与发起者。没有该用户的非空总结时先触发一次定向扫描；结果会作为回执发送到当前聊流。标记有效期 10 分钟，注入成功后消费。
- `clean`：删除 `private_summaries` 全部行，清空强制注入与粘性召回标记，回执形如「[ccr] 私聊回忆库已清空（删除 N 条总结）。」。
- 插件总开关关闭时，两条命令都不执行、不清库、不设标记，返回「插件未启用，命令未执行。」。

## 作用范围

四个名单，默认都为空（不限制）：

| 字段 | 作用 |
|---|---|
| `scope.group_whitelist` | 非空时仅名单内的群生效 |
| `scope.group_blacklist` | 命中即排除，优先于白名单 |
| `scope.user_whitelist` | 非空时仅名单内的用户被扫描/注入 |
| `scope.user_blacklist` | 命中即排除，优先于白名单 |

判定顺序：黑名单命中 → 拒绝；白名单非空且未命中 → 拒绝；否则放行。

生效位置：

- 群名单：`push` 计数、`planner` 注入、`reply` 注入，以及由这些路径触发的扫描。
- 用户名单：扫描候选（含 `reply` 模式的定向扫描）、`planner` / `reply` 常规注入选中的用户。
- 不适用：`recall_private_chat` 工具召回（只要求群聊，不查名单）、已登记的粘性注入、`/ccr debug test` 强制注入。也就是说，用户或群被排除后，已有概括仍可能被工具召回，或通过此前的粘性标记继续注入；需要彻底停止时，先 `/ccr clean` 清库，或停止插件后删除数据库。

## 配置

| 字段 | 默认 | 说明 |
|---|---|---|
| `plugin.enabled` | `true` | 总开关；关闭后扫描与注入停止，工具与命令返回未启用提示 |
| `plugin.config_version` | `"0.3.1"` | 隐藏字段，与插件版本同步，无需修改 |
| `scan.trigger_mode` | `"planner"` | `planner` / `push` / `reply`，见「扫描」 |
| `scan.scan_count` | `10` | 扫描候选消息数；`push` 模式下也是触发阈值；1–100 |
| `summarize.min_user_messages` | `5` | 窗口内用户消息数阈值；≥1 |
| `summarize.window_hours` | `24.0` | 总结窗口（小时）；≥0.1 |
| `summarize.resummarize_push_count` | `5` | 重总结推进数；≥1 |
| `summarize.model` | `"replyer"` | 任务名或具体模型名；留空则不传 |
| `summarize.max_tokens` | `1024` | 大于 0 时传入，0 表示不传 |
| `summarize.prompt` | `""` | 空 = 内置默认；支持 `{bot_name}` / `{user_nickname}` / `{user_id}` |
| `inject.inject_planner` | `true` | 是否注入 planner |
| `inject.inject_reply` | `true` | 是否注入 reply，也门控“仅粘性”分支 |
| `inject.planner_user_mode` | `"trigger"` | `trigger` / `recent_users` |
| `inject.recent_user_count` | `5` | `recent_users` 模式取最近多少条消息的用户；1–50 |
| `inject.reply_user_mode` | `"reply_source"` | `reply_source` / `follow_planner` |
| `store.summary_ttl_hours` | `24.0` | 总结保留时长（小时）；≥0.1 |
| `scope.group_whitelist` | `[]` | 非空时仅这些群生效 |
| `scope.group_blacklist` | `[]` | 命中排除，优先于白名单 |
| `scope.user_whitelist` | `[]` | 非空时仅这些用户被扫描/注入 |
| `scope.user_blacklist` | `[]` | 命中排除，优先于白名单 |
| `tool.recall_retention_minutes` | `5.0` | 召回的粘性时长（分钟）；0.5–1440 |
| `tool.context_window_messages` | `50` | 工具解析昵称的上下文消息数；5–200 |

各 Hook、工具和命令每次执行都直接读取当前配置，宿主热更新后立即按新值运行。bot 名称只在插件加载时读取一次：依次取宿主配置 `bot.nickname`、`person.bot_name`、`person.nickname`，都为空时用 `bot`；改名后需重新加载插件。

## 隐私与数据边界

- **读取**：群聊最近消息（用于确定候选用户、注入对象与 `push` 计数）；候选用户与 bot 的私聊窗口内消息（含 bot 的回复）。私聊只读，不修改。
- **发送**：除命令回执外，插件不会主动向会话发消息；私聊原文不会发送到群里。注入上下文的是概括，模型可能据此在回复中转述概括内容。
- **存储**：总结库只保存概括与元数据，不保存私聊原文。数据库路径见「安装与运行条件」。
- **外部请求**：私聊原文会作为总结请求的一部分发送给宿主配置的 LLM 服务（通过 `ctx.llm.generate`）；使用前应确认所用模型服务的数据处理策略。
- **日志**：DEBUG 日志记录总结请求中的私聊原文、LLM 返回全文与注入块全文，因此包含私聊内容；日志没有自动清理。
- **可触发者**：普通群成员无法直接查库，只能通过模型调用工具，且候选限定在当前聊流最近消息中出现过的用户，命中后一次返回一个用户的概括；操作员可用 `/ccr clean` 清库。模型是否调用工具由模型判断。
- **清理**：`/ccr clean` 删除全部概括并清除内存标记；过期概括按 TTL 淘汰；也可在插件停止后直接删除 `cross_chat_recall.db` 与 `logs/cross_chat_recall.log`。
- **范围限制的边界**：`scope.*` 不拦截工具召回、粘性注入与调试强制注入，见「作用范围」。

## 日志

- 文件：插件目录 `logs/cross_chat_recall.log`，DEBUG 级别，只写文件，不进入控制台或主进程日志。
- 内容：扫描开始/结束统计（候选数、总结数、入队数、跳过数、无私聊数、TTL 淘汰数、耗时）、每个用户的判定原因（消息数不足、重总结排队、失败冷却、无私聊流等）、总结 LLM 请求与返回、注入块全文、强制注入与粘性召回事件、异常堆栈。
- 没有轮转、自动清理或相关配置项；日志目录不可写时文件日志会静默关闭。
- 排查“为什么没有回忆”：先看扫描日志是否找到候选、是否因消息数不足/无私聊流/失败冷却跳过；再看注入日志是否因 TTL 过期或概括为空而没有插入。
